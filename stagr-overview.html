Product overview, design and roadmap  ·  September 2026

1. The problem this solves

Teams already have strong AI coding agents. What they lack is a safe, repeatable way to run those agents together, inside their own delivery pipeline, with clear rules about when a change may merge.

Today the common pattern is a do-it-yourself stack: one tool to implement, another to review, and existing CI as the only gate. Each piece is wired by hand, each repository does it differently, and nobody can answer simple governance questions with confidence:

  • Was every finding from the AI reviewer actually addressed before the merge?
  • Did the security review run on the exact commit that merged, or on an earlier one?
  • Can an untrusted contributor, or the AI implementer itself, bypass a required check?
  • How much did this pull request cost in model usage, and who capped it?
  • If the team switches model vendor or Git host next year, how much of this must be rebuilt?

The gap in the market. Mature tools each own one half of the pipeline: excellent implementers, excellent reviewers, non-AI CI gates. None ships the whole flow as one governed, configurable contract that binds any provider or model per stage and renders to any Git platform.

The answer in one sentence

agentic-foundation is the toolkit and its design; stagr is the installable product built from it. Together they turn one declarative file into a governed development lane on a repository's own CI: pick up an approved story, drive implement → review → security → tests → gated merge, and leave the pull request provably ready for a human to approve.

What it is

  • A platform-neutral configuration contract for a graph of SDLC stages
  • A deterministic installer and CLI (init, doctor, plan, apply)
  • Per-platform renderers that emit native CI workflows
  • Pluggable agent backends that wrap mature coding agents
  • A fail-closed merge gate and two clear merge lanes

What it is not

  • Not an AI agent; it composes agents that already exist
  • Not a runtime; it never executes a model call, test or scan itself
  • Not a hosted service or dashboard; it stays CLI + config + CI
  • Not a deployment tool or a project planner (those are sibling toolkits)
  • Not tied to one language, one AI vendor, or one Git host

2. How it works

stagr operates at render time only. An operator writes the contract, stagr writes the wiring, and the CI platform runs the work. Once rendered, the pipeline has no dependency on stagr at all.

Figure 1. The three-layer model. stagr lives only in the middle layer and is never a runtime dependency.

The control-plane rule

Declare, initialize, govern. Never execute. The litmus test for every feature is: "Does this require stagr to be running while the pipeline executes?" If yes, it belongs in the platform's generated artifacts or in a backend, not in stagr. The toolkit writes the wiring; the platform runs the work.

From zero to a governed lane in five steps

1

Install the CLI

A small Python package. No other runtime, no hosted service, no database.

2

Initialise the contract

A guided wizard detects the build toolchain (Python, Node, Go, Java, Rust, .NET) and proposes a profile.

3

Validate the contract, list the secret names to configure, and preview exactly which files would be written.

4

Render native workflows into the repository. Review the diff like any other change and merge it.

5

Work as usual

Open a pull request. The stages fire, the gates decide, and a human approves the merge.

✓

A version, a profile, a platform, and one model binding. Around ten lines for the common repository.

3. Design: layers and the stage graph

The design separates five concerns so that any one of them can change without disturbing the others. The contract never names a language, a vendor SDK, or a CI system directly.

Figure 2. Five layers. A team swaps a vendor, a coding agent, or a Git host by editing configuration, not workflows.

A pipeline is a graph of stages

Each stage is one agent in the software lifecycle: implement, review, security, test, integration-test, or custom. Every stage binds the same small set of properties, which keeps one generic abstraction for all stage kinds:

PropertyMeaning
Provider + modelThe knob. Mix vendors per stage, or vary the model across stages. Resolved most-specific-first: per-request override, then stage model, then organisation default. If nothing resolves, it fails loudly rather than guessing.
BackendThe executor. Derived from the provider by default; can be pinned or swapped by name. This is the agent-backend seam.
TriggerWhen the stage runs: pull request opened or updated, issue label, comment command, push, schedule, or manual dispatch.
GateWhat its result blocks. Advisory adds no required check. Blocking emits a required status check; missing, pending or errored means blocked.
DependenciesGraph edges that define order. Security gates ahead of integration and performance stages by default; a repository can reorder this.

4. The development lane

This is the heart of stagr: the ordered flow from an approved story to a merged pull request, and the gate that decides when the change is provably ready.

Figure 3. The development lane. Security gates ahead of the expensive stages; the gate rests the pull request ready for a human.

Profiles: simple by default, granular when needed

A profile expands to a default stage graph so a newcomer configures a handful of lines. Explicit stages merge onto the profile, so an expert can accept the standard graph and tweak just one stage.

ProfileStages it expands to
minimalimplement, review (advisory). Humans merge.
standardimplement, review (blocking), security (advisory).
fullimplement, security (blocking), test (blocking), integration-test (blocking), review (blocking).
customNo defaults. Every stage is declared explicitly.

5. Provably ready: the merge gate and trust model

A pull request is ready only when all of the following hold on the exact current commit. Every condition is fail-closed: a missing, pending or unknown signal means "not ready".

  • Eligible. Open, not a draft, not from a fork, targets the default branch, from a trusted author, and the platform reports no conflict.
  • CI green. The combined status and every latest check run on the commit is a clean success. The mandatory validate check must be backed by a trusted workflow run for this exact commit.
  • Every configured check green. SAST, quality, integration, test and custom checks, each a clean success. The configured list never hides an unrelated failing check.
  • Code review complete. When a blocking code review is configured, a review bound to this commit has completed and is clean.
  • Security review complete. When a blocking security review is configured, a review bound to this commit has completed and is clean.
  • Zero open review threads, from any stage, advisory or blocking.
  • No changes requested by any reviewer's latest decisive review.

Why the security review runs after the code review

Review backends reject a code review and a security review running concurrently on the same pull request. The security review is therefore triggered only after the code-review loop has converged: completed and clean on the exact commit. This is a correctness constraint, not a preference. Vulnerable code also should not consume integration or performance budget, so the security group gates ahead of those stages by default.

Trust boundaries

Trusted authors only

Automation is driven only by owners, members and collaborators on same-repository branches. Fork pull requests never drive automation.

Content is data, not instructions

Pull request, issue and comment text is untrusted input. An agent reviews or implements against it; it never obeys directives embedded in it.

Isolated identities and secrets

The implementer never reaches the publisher or the push credential. Secrets are referenced by name only and never logged or stored. Actions are pinned by commit hash with least privilege.

6. Key capabilities

Everything adapts to the team's own setup. All of the following are optional and configurable, so an organisation, a team, or an individual can bend the toolkit to how they host, deploy and observe.

CapabilityWhat it gives you
Any provider, per stageMix vendors freely: one vendor implements, another reviews. Adding a provider is a mapping entry, not a fork of the contract.
Layered model resolutionPer-request override, then stage model, then organisation default. Optional deterministic tiering runs trivial changes on a low-cost model and escalates large ones, with no extra model call.
Any platformOne contract, rendered per Git host. The renderer normalises pull vs. merge requests, roles and required checks.
Any languageA repository declares what "green" means through a preset (Python, Maven, Gradle, Node, Go, Rust, .NET) or custom commands. Stages never assume a language.
Skills and agent presetsReusable skills carry the methodology (checklist, rubric, output format). Presets wire a skill to a stage. Adopt a ready stage with one line, or bring your own by id.
Config inheritanceLayer an organisation base, a team base and a repository. Local values win.
Cost and token budgetsPer-run or per-period caps, global or per stage, with block, downgrade, or warn behaviour.
Prompt-injection guardrailsPull request, issue, comment and diff content is treated as data, never as instructions.
External quality gatesSonar, Checkmarx and similar tools are required by check name. stagr never runs the tool; it only requires its verdict.
ObservabilityRun records to a file, CI artifact, webhook, or telemetry collector. Endpoints come from a variable name, never hardcoded. Secrets always redacted.

The agent-backend seam

A backend is the executor that runs a stage's agent. stagr derives it from the provider and lets a stage pin or swap it by name. Adding a new backend is a new adapter template plus one enum entry, never a renderer rewrite. A backend always runs on the user's side of the line: in their CI runner or by dispatching to a provider's cloud, never inside a stagr-hosted process.

Configuration minimalism as a hard budget

"Configurable" must never mean "overwhelming". The common path is a handful of lines. Advanced blocks are opt-in and deleting any one falls back to a sensible default. The advanced surface is curated and capped, and no key duplicates something the CI system or Git host already owns. The design target: the typical repository is productive with about ten lines, and no repository ever needs more than a small, readable file.

7. Where stagr sits: the toolkit family

stagr owns exactly one span of the software lifecycle: from an approved story to a merged pull request. Nothing before, nothing after. Two sibling toolkits own the rest, and the three connect only through repository artifacts and a decision-event stream, never by calling each other directly.

Figure 4. Three toolkits, one contract family. stagr governs a single pull request's lane; it never schedules or monitors a fleet.

Non-goals that keep it a tool, not a framework

Not the planner

Feature intake, story breakdown and approval belong to the Planning toolkit.

Not the deployer

Release, deploy and promotion belong to the CD toolkit.

Not the orchestrator

Choosing which story to start and tracking many pull requests is an external job that consumes stagr's events.

Not a model gateway

Model calls never route through the toolkit. Only credential names and endpoint metadata are referenced.

Not memory or RAG

Knowledge and retrieval are a backend's concern.

Not a dashboard

CLI + config + CI. Events are emitted to the tools a team already uses.

8. Current state and roadmap

The roadmap is phased and honest. Each phase is control-plane work (declare, initialise, govern, render, emit), never runtime. Two decisions set the order: deepen GitHub first, and name the agent-backend seam now while shipping one GitHub-native backend.

What exists today

AreaStatus
ContractShipped  Platform-neutral schema, profiles, provider and model resolution, backend enum, budgets and guardrail policy.
Development laneShipped  Validate, review router, implementer, code review, security review, thread cleanup, fail-closed gate and both merge lanes rendered on GitHub.
TrustShipped  Commit-bound evidence, fail-closed gate, base-controlled definitions, scheduled sweep.
CLIShipped  init (guided wizard with toolchain detection), doctor, plan, apply.
DogfoodedShipped  The toolkit builds itself with the same pattern: AI implements, an independent AI reviews, CI gates, the fail-closed gate merges.
Governance limitsTarget  Loop caps, cost ceilings, circuit breaker and escalation states are declared but not yet enforced.
Audit streamTarget  Decision records and provenance are in scope; no emitter ships yet.
Other stages and platformsTarget  Test, integration-test and custom stages are validated but not rendered; only the GitHub renderer exists.

Guardrail for every roadmap item. Is this wiring and governance, or doing the work? If an item cannot be reduced to declare, initialise, govern, render or emit, it belongs in a backend, a sibling toolkit, or the user's own CI, not in stagr.

9. Why this shape wins

Every well-funded competitor is racing to be the agent, the editor, or the model. Almost no one is a neutral control plane that governs whatever agents a repository already has, inside the repository's own CI, and hands the merge decision to a human.

Structurally defensible

Neutrality is off-limits to platform incumbents, because each wants lock-in. It needs no model training and no hosted runtime to build.

Composes, never competes

The best implementers and reviewers keep improving. stagr gets better with them, because it is the seam they plug into.

Governance people can trust

Commit-bound evidence, fail-closed gates, isolated identities, secrets by name. "Provably ready" is a checklist, not a feeling.

Portable by construction

One contract; a new vendor is a mapping entry, a new agent is an adapter, a new Git host is a renderer. Never a rewrite.

In summary

  • One file in, a governed lane out. Ten lines of configuration for the common repository.
  • The toolkit writes the wiring; the platform runs the work. stagr is never a runtime dependency.
  • Any provider, any agent, any platform, any language. Mixed freely, per stage.
  • Humans keep the final word. The default lane ends at "ready for approval"; auto-merge is opt-in and a label always stops it.
  • Already running. The toolkit builds and reviews itself with the same lane it ships.
